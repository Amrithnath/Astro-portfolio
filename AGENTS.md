# AGENTS.md

## Source Of Truth
- Trust `package.json`, `astro.config.mjs`, and `.github/workflows/*` over `README.md` when they disagree.
- CI is the runtime truth: Node 26 current release line (pinned in `.nvmrc`); Node 24 must keep working (`engines` `>=24` for Vercel; CI builds on 24 and latest), pnpm 12 (pinned via `packageManager`; dependency build scripts must be allowlisted in `pnpm-workspace.yaml` `allowBuilds` and `onlyBuiltDependencies`; keep `pmOnFail: ignore` so the lockfile stays single-document for pnpm 9/10 on Vercel), preview on port `4321`.

## Commands
- Install with `pnpm install --frozen-lockfile` to match CI.
- Use `pnpm dev` for local development.
- Use `pnpm check` for Astro/TypeScript diagnostics (TypeScript 6, whose defaults include `strict`; `astro check` refuses TypeScript 7, so Dependabot ignores 7.x) and `pnpm build` to generate the static site.
- Use `pnpm check:seo`, `pnpm check:theme`, and `pnpm check:links` to validate the built `dist/`; `pnpm verify` builds and runs them plus `pnpm check:headers` and `pnpm check:csp` (including focused policy tests).
- `public/_headers` is the source of truth for response headers. Vercel ignores it, so after editing it run `pnpm sync:headers` to regenerate `vercel.json`; `pnpm check:headers` fails on drift.
- CSP: `public/_headers`'s `HTML-CSP` comment feeds the `portfolio-csp` build hook (`scripts/csp.mjs`), which inserts a meta after charset and before resources with shared build-wide script hashes for ClientRouter. Do not add header `default-src`/`script-src` without matching hashes: both policies intersect. Keep `frame-ancestors` in the header. Built HTML must have no inline handlers or `javascript:` URLs; JSON-LD is inert. Keep `style-src 'unsafe-inline'` for inline attributes/Shiki, Astro styles and the inherited resume print policy. Astro's built-in CSP does not support ClientRouter. Scripts opt out of Rocket Loader; preserve `no-transform` against Cloudflare email/beacon injection. `pnpm check:csp` validates every built document including offline; `/admin/` keeps its own policy. E2E applies the response CSP as well as meta and observes policy violations.
- Use `pnpm exec playwright install chromium` once (or set `PLAYWRIGHT_CHANNEL=chrome` to use installed Chrome, as CI does), then `pnpm test:e2e` after building for Chromium smoke tests and axe-core accessibility checks (`tests/e2e/a11y.spec.ts`, fails on serious/critical WCAG 2.1 AA violations). The test runner starts its own preview on port `4321`; use `PORT=4326 pnpm test:e2e` if that port is occupied.
- Visual regression is separate: `pnpm test:visual` covers six routes (including about) × terminal/light × desktop/mobile (`tests/e2e/visual.spec.ts`). CI uses Ubuntu/Chrome and platform-separated snapshots. Use Actions → **Update visual baselines** (`visual-baselines.yml`) on the target writable branch to generate/review/commit Linux baselines, then manually run Portfolio Quality (token commits do not trigger CI). Missing Linux PNGs skip with notices; existing baselines gate deploys and upload diffs on failure. Never commit macOS baselines as Linux truth; disposable `PLAYWRIGHT_CHANNEL=chrome pnpm test:visual --update-snapshots` creates Git-ignored Darwin images. Keep dynamic content masks and font/deferred-load waits intact.
- Lighthouse: after building, run `pnpm lighthouse` (mobile) and `LIGHTHOUSE_DESKTOP=1 pnpm lighthouse` (desktop). Chrome/Chromium must be installed (`CHROME_PATH` can select it). Each audits six routes three times; Accessibility, Best Practices and SEO medians must be 100; Performance must be at least 95 (error budget for CI variance). `LIGHTHOUSE_SHARD=<index>/<total>` audits a subset of routes (CI runs 2 shards per profile). Reports are saved under `.lighthouseci/reports/{mobile,desktop}[-<shard>]/`; the next collection replaces raw `.lighthouseci/` runs. The static server does not apply Cloudflare `_headers`, so header diagnostics are informational, not production-header verification.
- Dependabot (`.github/dependabot.yml`) opens one weekly Monday PR for all npm updates (majors included) and one for Actions, plus grouped security PRs, with a 1-day cooldown matching pnpm `minimumReleaseAge`.
- CI (`.github/workflows/ci.yml`, "Portfolio Quality") runs fail-fast in parallel: Conventions, CodeQL, Build and Node 24 together; E2E, Visual and Lighthouse after Build (they reuse its `dist` artifact); deploys after all pass. A failing gate cancels the run via `gh run cancel`, so new gate jobs need `actions: write` and the same final step. Runs on PRs and pushes to `main`. There is no lint script. A `Changes` job (`scripts/ci-changes.mjs`, tested by `pnpm test:ci`) skips site gates (Build, Node 24, E2E, Visual, Lighthouse, deploys) unless a change can affect the site, and skips CodeQL for docs-only changes; when adding a path that is not part of the site build, list it there, because unknown paths run everything. It also skips all gates on release-only diffs (changelog, manifest, `package.json` version) and runs only Build and the deploys when such a diff lands on `main`. Lightweight jobs (git, API calls, deploy uploads, small Node tests) use `ubuntu-slim` with `timeout-minutes` ≤ 10 (hard limit 15). Builds, CodeQL, browsers, Lighthouse and image processing stay on `ubuntu-latest`.
- To mirror CI preview checks, run `PORT=4321 pnpm preview` and smoke-test the route with `curl -f http://localhost:4321/<route>`.

- Build performance: keep Astro route concurrency at its default (2/4/CPU-count trials did not help). The Build job caches only `node_modules/.astro/assets` with an exact lockfile/config/source/public-input key; do not cache `dist`, rendered HTML, or the content store. Preserve the single-parse CSP injection and verify its original-offset edits with `pnpm check:csp`.

## Architecture
- Source is grouped under `src/features/{content,photos,resume,seo,terminal,theme,views}/`; feature-owned components, helpers, data and CSS live together. Cross-feature head/document composition, generic UI, date/build helpers and global CSS live in `src/shared/`. Keep Astro routes and collection inputs in `src/pages/` and `src/content/`.
- Imports remain relative so Node-run scripts/tests need no alias loader. Workers keep their existing root commands and paths; the root-only pnpm workspace deliberately excludes `project-archive/`.
- This is a single-package Astro 7 site with `output: 'static'`; do not add SSR-only or server endpoint features to the Astro app.
- `src/pages/index.astro` is a special homepage entrypoint: it does not use `src/shared/layouts/BaseLayout.astro` but renders the same `src/features/terminal/TerminalShell.astro` (window chrome, `TerminalNav` tabs, status bar, footer) and fetches deferred terminal HTML from `src/pages/terminal-full.astro`.
- Homepage content is assembled from `src/features/resume/landing-data-service.ts` and `src/features/resume/resume-compendium.ts`, not from one static data file.
- Interior routes use `src/shared/layouts/BaseLayout.astro`, which renders terminal nav/footer and one content slot, and can replace the page with a WIP screen via `src/features/terminal/wip.ts` (independent of themes).
- Blog Markdown lives in `src/content/blog/`; projects live in `src/content/projects/` (preserve case-sensitive subfolders such as `webDev/`). `src/content.config.ts` defines Content Layer glob loaders and Zod schemas; IDs are file paths without `.md` so existing URLs remain stable.
- To add a post/project: create a Markdown file in the corresponding collection with `title`, `description`, and `pubDate` (ISO date). `tags` defaults to `[]` and `draft` to `false`; `updatedDate`, `img`/`image` (absolute URLs or site paths like `/images/blog/x.jpg`), and `lang` are optional. Projects also accept optional `link`, `client`, `github`, `live`, `demo`, `tech`, `status`, and `featured`; blog posts can reference a project ID for linked write-ups. Projects and blog posts share ArticleLayout, and the projects index renders filterable cards with related write-up counts. Do not add `layout:` frontmatter. Dynamic `/blog/[...slug]` and `/project/[...slug]` routes render the existing layouts. `draft: true` is available in development but excluded from production routes, lists, Markdown mirrors, LLM discovery, sitemap, and RSS.
- All collection consumers use `src/features/content/content.ts` (`getCollection` with shared draft filtering and URL generation). `/rss.xml` lists published blog posts; `BaseHead.astro`, `/llms.txt`, and `/robots.txt` advertise it. Markdown mirrors use collection bodies; the profile compendium remains separate.
- Markdown project/blog layouts delegate to `src/features/content/ArticleLayout.astro` and then `BaseLayout`; preserve their article SEO props.
- `src/shared/components/BaseHead.astro` owns SEO, theme bootstrap, token/shell CSS, icons, manifest, and production-only service worker registration. The homepage, redirects, and `/terminal-full/` also use it; do not duplicate head logic or content for themes.
- `/terminal-full/` is a noindex HTML document; the homepage extracts only `[data-terminal-fragment]`, containing commands without a second terminal shell or footer.
- Navigation is full page loads with native cross-document view transitions (`@view-transition` in `global.css`) plus Astro prefetch. Do not reintroduce ClientRouter: it copies the server `<html data-theme>` default on each swap and flashes/loses the chosen theme. Page scripts initialize directly (module scripts run once per page) and must not listen for `astro:page-load`.
- Static `/og/*.png` endpoints render 1200×630 terminal social cards with resvg and bundled OFL Fira Code; `src/features/seo/og.ts` owns page mapping. Keep SEO image dimensions and build checks aligned.
- `Analytics.astro` (in `BaseHead`) renders the Cloudflare Web Analytics loader only when `PUBLIC_CF_BEACON_TOKEN` is set at build time (CI passes `vars.CF_BEACON_TOKEN`). It loads only on the `site` hostname and honours GPC/DNT; it is cookieless. The CSP already allows `static.cloudflareinsights.com` and `cloudflareinsights.com`. Keep the privacy policy in sync with it.
- `ViewCount.astro` (blog/project articles via `ArticleLayout`) renders only when `PUBLIC_VIEWS_URL` is set at build time (CI passes `vars.VIEWS_URL`). It GETs counts from `workers/views/` (Cloudflare Worker + D1, deployed by `.github/workflows/views.yml` with var `VIEWS_D1_DATABASE_ID`; test with `pnpm test:views`) and POSTs once per path per browser only on the `site` hostname without GPC/DNT. The Worker must stay fail-closed (path allowlist, exact `ALLOWED_ORIGINS`, rows only for live pages) and never read or store IP/UA/cookies. Keep `connect-src` in `public/_headers` and the privacy policy in sync.
- `SiteFooter.astro` (end of `TerminalFooter`, every page) is the tmux-style site status line: live widgets left, version/commit centre, privacy/scan/rss/source right; put future site-wide widgets there as `.status-segment`s. Its `CarbonBadge.astro` is a native Website Carbon badge: only on the `site` hostname without GPC/DNT it GETs `api.websitecarbon.com/b` (no credentials/referrer, cached a day in localStorage) and otherwise or on failure shows a local SWD v4 estimate (`src/features/terminal/perf.ts`). Never load the official unpkg badge script. Keep `connect-src` and the privacy policy in sync.
- `ServiceWorker.astro` registers `/sw.js?v=<build>` after load, only in production. `src/shared/lib/build-version.ts` supplies one shared version per build.
- `/admin` (`src/pages/admin/index.astro` + `public/admin/config.yml`) is the Sveltia CMS editor: noindex, exempt from SEO/theme checks, bypassed by the service worker, with its own CSP/COOP in `public/_headers`. Keep `@sveltia/cms` pinned (pnpm `minimumReleaseAge` rejects releases under 24h). CMS saves open PRs from `cms/*` branches; CI skips the PR-title check for those but still runs commitlint, so keep `commit_messages` conventional. Sign-in goes through `workers/cms-auth/` (Cloudflare Worker, deployed by `.github/workflows/cms-auth.yml`; test with `pnpm test:cms-auth`); it must fail closed and only post tokens to `ALLOWED_DOMAINS` origins.
- The wedding stack is paused in `project-archive/` (see its README); it is not built, and its hooks in `astro.config.mjs` and `public/_headers` are commented out. Do not change it as part of portfolio work. The public `/offline/` fallback is deliberately self-contained and terminal-only.
- `/privacy-check/` (`src/features/privacy/`) is a **listed** terminal page: visitors type `run check [--offline] [--stun]`, `run check --help` or `explain <id>`. `checks.ts` holds pure parsers/verdicts and education text (tested in `tests/shell/privacy.test.mjs`); `probes.ts` holds browser probes. It must never send or store results: no analytics (`BaseHead.astro`), a local-only `CarbonBadge`, and the only requests are `/pagead/ads.js` (blocker bait, bypassed by the service worker), `endoflife.date` (scoped `connect-src` in `public/_headers` and `scripts/csp.mjs`) and opt-in Cloudflare STUN. Keep `run check --help`, the page disclosure and the privacy policy accurate when probes change.
- `pnpm build` runs Pagefind after Astro, writing `dist/pagefind/`. Only indexable `TerminalShell` main content gets `data-pagefind-body`; Pagefind requires that selector (`pagefind.yml`), so unlisted, redirect, fragment and offline pages never enter the index. Keep this boundary when adding layouts. `/search/?q=...` uses a lazy same-origin API and token-based UI, not Pagefind UI CSS. Its scoped CSP permits WebAssembly; the service worker bypasses `/pagefind/` to avoid stale indexes. Search omits the analytics loader to keep queries private. No search service or credentials are needed.

## Navigation And Routing
- New pages ship **unlisted** until the owner says otherwise: deploy them, but add the prefix to `excludedPrefixes` in `src/features/seo/seo.ts` (noindex, robots Disallow, no sitemap/LLM entry), add an `X-Robots-Tag` block to `public/_headers` (then `pnpm sync:headers`), add it to the unlisted loop in `scripts/check-agentic-seo.mjs`, and do not link it from `TerminalNav`, `navigation.ts` or any other page. `/photography/`, `/now/`, `/uses/` and `/search/` are currently unlisted.
- `/photography/` and every subroute stay unlisted; only photography pages may link to them. `photos` YAML uses exactly one local `image` or R2 `remote` source, normalized kebab-case tags, optional structured location (coordinates ≤2 decimals), and references to `albums`. Albums with `kind: trip` have ordered stops and dates; drafts are excluded in production. Never invent locations for seed images. Reserved photo IDs: `tags`, `places`, `albums`, `map`, `prints`, `feed`, `feed.xml`, `rss`, `rss.xml`.
- Photography helpers/config: `src/features/photos/photos.ts`, `src/features/photos/config.ts`; gallery scripts initialize on load. `pnpm test:photos` tests pure indexing and GPS-bearing synthetic offline ingest; `pnpm check:photos` rejects local GPS EXIF/uncatalogued images. R2 originals stay in the private inbox/archive; only stripped AVIF/WebP derivatives go to the separate public bucket. `pnpm photos:ingest -- <files> --dry-run --out .photos-output` needs no credentials; `.github/workflows/photos.yml` ingests the inbox using secrets and creates draft metadata PRs for owner review. Setup is documented in README Photography.
- Individual photo pages use `PhotoViewer.astro`: the native modal opens with the current display image, then dynamically imports `src/features/photos/photo-viewer.ts` for WebGL quad zoom/pan (CSS-transform image fallback). Use only existing metadata-free derivatives (largest WebP ≤2400px), never originals. Remote texture images must set anonymous CORS before `src`; public R2 GET CORS must allow the site/needed previews, and missing CORS must retain CSS viewing. No new CSP origin is needed. Keep direct script initialization, Rocket Loader opt-out, keyboard/touch controls, focus return and reduced-motion behavior; `tests/e2e/photos.spec.ts` covers these. Tiling/higher-resolution ingest is deferred.
- Photography extras stay under the unlisted prefix: `/photography/map/` bundles a public-domain Natural Earth outline (attribution in `src/features/photos/world-land.json`), uses only coarse coordinates, and makes no external map requests; `/photography/rss.xml` is advertised only inside photography. EXIF panels use an explicit non-GPS allowlist; ingest/CMS support optional focalLength (mm), aperture, exposureTime (seconds), iso. `/photography/prints/` remains clearly PLACEHOLDER until owner-supplied terms/prices exist; use the profile contact, never invented details.
- Photo locations may come from a `location.maps` Google Maps link: `src/features/photos/geo.ts` parses full links in the schema (name plus rounded coordinates; the link is never rendered). `pnpm photos:locate` and `.github/workflows/photos-locate.yml` (same-repo photo PRs) expand short links, reverse-geocode missing names via OpenStreetMap Nominatim (rounded coordinates only, max 1 request per second, attribution shown on place pages), and strip the link. Ingest names EXIF GPS the same way; dry-run geocodes only with `--geocode` or `--maps`. Tests mock all network calls.
- `/now/` (`src/pages/now.astro`, single-entry `now` collection at `src/content/now/now.md`, CMS *Pages → Now*) is unlisted and currently placeholder text. Do not invent personal content for it.
- `/uses/` (`src/pages/uses.astro`, single-entry `uses` collection at `src/content/uses/uses.md`, CMS *Pages → Uses*) follows the same pattern: unlisted, placeholder gear lists. Do not invent gear.
- Route additions are manual across multiple surfaces; update every relevant file yourself.
- Update `src/features/terminal/TerminalNav.astro` (shared by homepage and interior pages via `TerminalShell`).
- Update `src/features/terminal/navigation.ts` if the route should appear in terminal `ls` output.
- `/blog/` (`src/pages/blog/index.astro`) is the real blog index (published posts newest first, empty state when none). `/blogs` is a single edge 301 to `/blog/` via `public/_redirects`, mirrored into `vercel.json` by `pnpm sync:headers`; `src/pages/blogs.astro` is only a meta-refresh fallback for local preview. Add new redirects to `public/_redirects`, not as redirect pages.

## Styling And Themes
- Do not assume Tailwind; styling is plain CSS in `src/features/theme/styles/`, `src/features/terminal/terminal-theme.css`, and `src/shared/styles/` plus page/component-local styles.
- `terminal` (dark) and `light` (warm paper: cream transcript, sand chrome, AA ANSI inks) are registered. Render each page/component once; never add hidden per-theme views or repeated IDs.
- `src/features/theme/index.ts` is the typed registry (`id`, `label`, `colorScheme`, `themeColor`, `defaultTheme`). All portfolio documents render `data-theme="terminal"` on `<html>` for no-JS defaults.
- `ThemeBootstrap.astro` runs inline in the head before paint, validates persisted `portfolio-theme`, migrates a valid legacy `portfolio-layout-theme` only when the new key is absent, removes the legacy key, and falls back safely when storage is invalid/blocked. `window.__theme.current` is the resolved theme; `preference` is `auto` or an explicit id. `set(id)` / `auto()` return false for invalid IDs and emit `portfolio:theme-change` with `detail.theme` and `detail.preference` on valid changes. Auto (no stored key) follows `prefers-color-scheme` before paint and on live changes; explicit choices persist. Storage events synchronize tabs. `ThemeSwitcher.astro` renders the keyboard/click `:set background= [auto] [dark] [light]` button group in `TerminalShell` status-right, hidden without JS and omitted when fewer than two themes exist.
- To add a theme: (1) register a unique id and metadata in `src/features/theme/index.ts`; (2) add `src/features/theme/styles/themes/<id>.css`, scoped to `[data-theme="<id>"]`, defining every semantic and terminal palette token in `terminal.css`; (3) import that file in `BaseHead.astro`; (4) optionally add `[data-theme="<id>"]` component overrides (use `:global([data-theme="<id>"])` in scoped Astro styles); (5) if exposing selection, build a switcher from `themes` only when `themes.length > 1` and call `window.__theme.set(id)` (`auto` clears the stored choice). Initialize directly on each document load with a duplicate-handler guard; never use `astro:page-load`. Do not clone content or add theme-specific route layouts. See `src/features/theme/README.md`.
- Markdown syntax highlighting in `astro.config.mjs` uses semantic CSS tokens, not a fixed Shiki palette.
- Shell styling in `src/features/terminal/terminal-theme.css` is theme-independent and consumes tokens; prefer `var(--color-bg)`, `var(--color-text)`, `var(--color-surface)`, `var(--color-border)`, `var(--color-link)`, and `var(--color-accent)` for new components. Existing terminal palette aliases remain supported.
- Verify theme changes with `pnpm build`, `node scripts/check-agentic-seo.mjs`, and `node scripts/check-theme-system.mjs` (built HTML, storage/API, and single-instance resume exports/toggles).
- Token layers: `src/features/theme/styles/tokens.css` (theme-agnostic spacing `--space-1..8`, type `--text-xs..3xl`, line-heights, `--radius-*`, `--content-width`, `--shell-width`, `--shell-padding`, z-index, transitions) and `src/features/theme/styles/themes/<id>.css` (colors only: semantic `--color-*`, `--window-control-*`; `--terminal-*` are aliases). Do not hardcode hex/rgb outside theme files, the resume print `--print-*` block, and `public/offline/index.html` (static token snapshot).
- Primitives: `src/shared/ui/{TerminalWindow,Prompt,Card,Button}.astro`, shared classes in `src/shared/styles/ui.css`, and `.prose` in `src/shared/styles/prose.css` (use for Markdown/long text). Prompt commands are syntax-highlighted at build time via `ShellCommand.astro` + `src/shared/lib/shell-highlight.ts` (`pnpm test:shell`). Pages should use these instead of page-local CSS; `TerminalShell` is the single shell for all pages.
- `src/shared/styles/global.css` sets `*, *::before, *::after { box-sizing: border-box; }`. Breakpoints (not usable as custom properties): `48rem` (md) and `64rem` (lg); `min-width: 110rem` is reserved for the wide-screen side panes (`SidePanes.astro`: per-page man/career and profile/skills panes via the `panes` prop; link only listed routes, photography links only on photography routes). Links use `--color-link` (hover `--color-accent`), fonts `--font-mono`; animations must respect `prefers-reduced-motion` (global rule exists).

## Versioning And Releases
- `package.json` and `.release-please-manifest.json` are the source of the current application version. The site footer reads that version at build time, and `/version.json` reports it with the build commit and timestamp; its response must remain revalidated (`public/_headers`).
- Use `<type>(<optional scope>): <emoji> <subject>` for PR titles and commits. The Conventional Commit type must be first and the subject must start with the actual Unicode emoji (not a shortcode). Preferred type-to-emoji mapping: `feat` ✨, `fix` 🐛, `perf` ⚡, security fixes (`fix`) 🔒, `refactor` ♻️, `docs` 📝, `ci` 👷, `build` 📦, `chore` 🔧, `style` 💄, `test` ✅, and `revert` ⏪. Breaking changes use `feat!: 💥 ...`. Examples: `feat: ✨ add version endpoint` and `feat!: 💥 replace public API`. Security fixes use `fix: 🔒 ...`, not a `security:` commit type. `pnpm commitlint --from <base> --to <head>` checks a commit range locally; PR checks validate titles and commit messages.
- Release Please runs on pushes to `main`, opens/updates a release PR from conventional commits, and creates the `vX.Y.Z` tag and GitHub release when that PR is merged. It updates the package version and generated `CHANGELOG.md`. Do not hand-edit the changelog after the seeded 2.0.0 entry. A `RELEASE_PLEASE_TOKEN` secret is optional: configure a PAT if release PRs must trigger other `GITHUB_TOKEN`-driven workflows, because GitHub suppresses most downstream workflow runs for events created with `GITHUB_TOKEN`; otherwise the default token is sufficient.
- One-time 2.0.0 bootstrap after the integration branch is merged and pushed to `main`: to avoid Release Please proposing or publishing 2.0.0 again, create the initial release at that exact merge commit before relying on subsequent automation. On `main`, run `git tag -a v2.0.0 -m 'Release v2.0.0' <merge-commit-sha>`, push it with `git push origin v2.0.0`, then create a GitHub release for the existing `v2.0.0` tag (the seeded changelog documents the release). The next conventional changes on `main` will then produce a 2.0.1/2.1.0 release PR as appropriate. Do not tag the feature branch tip if its merge creates a different commit. Alternatively, leave off the initial tag and let Release Please bootstrap, but review its first PR/tag carefully and do not also create a manual 2.0.0 release.
